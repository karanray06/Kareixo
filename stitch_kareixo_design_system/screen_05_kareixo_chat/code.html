Why is this query performing so poorly in production? It's taking ~850ms on our 4M row user table:

users_query.sql PostgreSQL 
SELECT id, email, role, created_at 
FROM users 
WHERE LOWER(email) = LOWER($1) 
  AND status = 'active'
ORDER BY created_at DESC 
LIMIT 1;
smart_toy
Kareixo Engine GEMINI 1.5 PRO · 10:14 AM

The query is performing a sequential full-table scan because LOWER(email) invalidates the standard B-tree index on email. Even though an index exists on that column, PostgreSQL cannot utilize it when the indexed column is wrapped in an expression without a corresponding functional index.

warning Root Cause

Expression Impedance: wrapper prevents B-Tree lookup.

speed Scan Cost

Seq Scan over 4,120,850 rows (planner cost ~48,210.00).

auto_fix_high Suggested Solution

Functional expression index + composite ordering key.

Recommended DDL & Query Plan Estimated: 850ms → <1.4ms

-- 1. Create a functional expression index with active condition filter
CREATE INDEX CONCURRENTLY idx_users_lower_email_active
ON users (LOWER(email), created_at DESC)
WHERE status = 'active';

-- 2. Query execution drops from 850ms to <1.4ms (Index Scan)
SELECT id, email, role, created_at
FROM users
WHERE LOWER(email) = LOWER($1) AND status = 'active'
ORDER BY created_at DESC LIMIT 1;

Since api-service uses raw SQL migrations via Kysely / node-pg (detected in src/db/migrations/), here is the transactional migration with zero-downtime safety:

description src/db/migrations/20260907_add_lower_email_index.sql 
-- Up Migration
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_users_lower_email_active
ON users (LOWER(email), created_at DESC)
WHERE status = 'active';

-- Down Migration
DROP INDEX CONCURRENTLY IF EXISTS idx_users_lower_email_active;
info
Safety requirement for CONCURRENTLY: PostgreSQL prevents running concurrent index builds within an explicit transaction block (BEGIN ... COMMIT). Ensure your migration runner executes this with disableTransactions: true.
